# justEMT Next.js Post-Migration Audit — 2026-09

## Scope

This audit reviews the current `master` state after the Astro → Next.js migration and tracks the hardening work applied on branch `audit/hardening-nextjs`.

Reviewed areas:

- Next.js App Router structure and deployment configuration
- authentication and session cookies
- API route authorization boundaries
- shared storage and rate limiting
- AI chat / Tavern cost controls
- Cloudflare R2 gallery upload and manifest consistency
- visitor statistics correctness and privacy
- Markdown rendering / DOM XSS boundaries
- mobile hero loading behavior
- repository documentation and CI

## Executive summary

The migration itself is structurally sound. The repository is a real Next.js 16 App Router application rather than an Astro project wrapped in Next.js. No critical secret exposure or client-only authorization bypass was found.

The main problems were application-level correctness and hardening gaps rather than framework choice. This branch fixes the highest-value issues without another architectural rewrite.

## Fixed in this branch

### P1 — private blog metadata disclosure

**Before:** private article body access was protected, but `generateMetadata()` could still return the private title and description to an unauthenticated request.

**Fix:** private metadata now performs the same session check. Unauthenticated requests receive generic metadata plus `noindex`, `nofollow`, and `noarchive` directives. Authenticated private pages also remain non-indexable.

### P1 — mobile hero downloaded desktop artwork

**Before:** the CSS treated multiple `background-image: url(...)` entries as fallbacks. They are actually stacked layers, so mobile rules could request both the mobile image and the multi-megabyte desktop image.

**Fix:** `src/app/wallpaper.css` is imported after the legacy global styles and gives each theme/viewport combination exactly one bitmap URL:

- light desktop → `hero-light.jpg`
- light mobile → `hero-light-mobile.jpg`
- dark desktop → `hero.jpg`
- dark mobile → `hero-dark-mobile.jpg`

Gradients remain layered above/below the selected image.

**Follow-up:** recompress the two desktop JPEG files to modern AVIF/WebP variants. The duplicate-request bug is fixed, but the desktop source files are still larger than desirable.

### P1 — AI daily quota could be exhausted in a burst

**Before:** anonymous chat had a global daily cap but no short-term client limit. One visitor could rapidly consume the entire anonymous allowance. Authenticated chat had no short-term guard either.

**Fix:** `/api/chat` and `/api/tavern` now share the same fixed-window limiter:

- anonymous: 5 requests / minute / IP
- authenticated: 20 requests / minute / IP

The two endpoints intentionally use the same scope so alternating between Chat and Tavern does not double the allowance.

### P1 — music proxy could be used to burn upstream quota

**Before:** IDs were correctly restricted to the configured playlist, but a client could still generate many valid cache misses and consume the site's daily music API allowance.

**Fix:** public music actions except quota inspection are limited to 12 requests / minute / IP.

### P1/P2 — authentication limiter was process-local

**Before:** login and visitor-reset password attempts were protected by an in-memory `Map`. On Vercel, each instance had an independent counter.

**Fix:** security-sensitive limits now use the shared Store. With Upstash configured they are cross-instance. If Redis is configured but unavailable, authentication-related limits fail closed instead of silently becoming per-instance protection.

Local development can still run without Redis and uses the in-memory fallback.

### P2 — lifetime visitor counters expired after one year

**Before:** `visitors:total` and `visitors:unique:total` used a 365-day TTL, while the Store intentionally did not renew TTL during `INCR`. The counters would therefore eventually reset to zero.

**Fix:** Store counters can now be explicitly persistent. Calling persistent `incr()` also issues Redis `PERSIST`, so an existing legacy total key is migrated in place instead of keeping its old expiration.

The lifetime `seen` marker is also persistent; Redis keys use a SHA-256-derived internal visitor identifier rather than storing the browser UUID directly.

### P2 — R2 manifest lost updates under concurrency

**Before:** gallery writes followed read → modify → unconditional overwrite. Two simultaneous operations could both read version N and then overwrite one another.

**Fix:** manifest writes now use R2 optimistic concurrency control:

1. read `gallery/manifest.json` and retain its ETag;
2. calculate the mutation;
3. update with `If-Match: <etag>`;
4. on first creation use `If-None-Match: *`;
5. retry a conflicting 409/412 with a fresh manifest.

This works independently of Upstash and protects cross-instance writes at the storage object itself.

### P2 — abandoned presigned uploads polluted final gallery prefixes

**Before:** presigned uploads wrote directly into permanent `originals/`, `previews/`, and `thumbnails/` keys. Closing the page before commit could leave permanent orphan objects.

**Fix:** direct uploads now go to:

```text
gallery/staging/<uuid>/
```

Commit performs size/hash validation, copies the verified staging objects to their permanent keys, updates the manifest, then deletes staging objects.

**Required deployment action:** configure an R2 lifecycle rule for prefix `gallery/staging/`, for example deletion after 1 day. This cleans abandoned uploads that never reach the commit endpoint.

### P2 — baseline response hardening

Added globally:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- restrictive `Permissions-Policy`
- `Cross-Origin-Opener-Policy: same-origin`

A strict CSP is intentionally not enabled in this branch. Next.js hydration plus the pre-hydration theme script should first move to a nonce-aware policy. Adding a CSP with broad `unsafe-inline` merely to make it pass would give a false sense of protection.

### Engineering — CI and documentation drift

Added:

- `npm run typecheck`
- `npm run check`
- `.github/workflows/ci.yml`

The PR workflow runs dependency installation, TypeScript checking, and a production build.

Updated or removed stale Astro assumptions in:

- `README.md`
- `docs/chat-architecture.md`
- `.vscode/extensions.json`
- the introductory blog post

The dedicated historical Astro article is intentionally retained because its subject is Astro rather than being runtime documentation.

## Security observations that were already good

The following existing boundaries were preserved:

- `AI_API_KEY`, music API credentials, R2 credentials and `AUTH_SECRET` stay server-side.
- production does not accept the development fallback `AUTH_SECRET`.
- session cookies are HttpOnly and use `Secure` in production plus `SameSite=Lax`.
- password comparison uses `timingSafeEqual`.
- gallery mutation endpoints verify the signed admin session server-side.
- chat message structure and maximum length/count are sanitized server-side.
- model output is rendered through DOM text nodes rather than raw model-provided HTML.
- blog HTML is currently sourced only from repository-controlled Markdown.
- AI requests have an application timeout below the function duration ceiling.
- quota is refunded when an upstream AI request produces no output.

## Known remaining risks / deferred work

### P2/P3 — no strict CSP yet

Implement a nonce-based Content Security Policy rather than an `unsafe-inline` policy. This requires coordinating Next.js-generated scripts and the early theme initializer.

### P2/P3 — desktop hero source files remain large

The request-selection bug is fixed, but the desktop JPEG assets should still be converted/compressed. Targeting a few hundred KB per desktop wallpaper would materially improve cold-load performance.

### P3 — public visitor records are still linkable

Recent records expose a stable short `visitorKey` plus partially masked IP information. For a stronger privacy posture, rotate the display identifier daily (or remove it entirely) and consider displaying less IP information publicly.

### P3 — Tavern state is not authoritative

Tavern v1 accepts browser-supplied persona/state/memory after structural sanitization. A user can edit local storage and set trust/affinity/relationship values manually. This is acceptable for the current PoC but not for a trusted relationship engine.

The v2 boundary should keep authoritative state and memory transitions server-side, ideally backed by PostgreSQL.

### P3 — large client components

The following components remain relatively large and should be decomposed only when active feature work touches them:

- `chat-page.tsx`
- `tavern-page.tsx`
- `music-player.tsx`
- `gallery-client.tsx`
- `manage-script.tsx`

Do not perform another broad rewrite solely for file-size aesthetics. Extract hooks and domain components incrementally with tests.

## Deployment checklist

Before merging/deploying this branch:

1. Ensure production has a long random `AUTH_SECRET`.
2. Configure Upstash Redis for accurate cross-instance counters and rate limits.
3. Leave `TRUSTED_IP_HEADER` empty on normal Vercel deployment; set it only for a trusted self-hosted proxy topology.
4. Verify R2 credentials remain bucket-scoped.
5. Add an R2 lifecycle rule deleting `gallery/staging/` objects after ~1 day.
6. Ensure R2 CORS allows `https://<site-domain>` and `http://localhost:3000` for `PUT` during development.
7. Verify `npm run typecheck` and `npm run build` pass in CI.
8. Test login, private blog routing, one gallery upload/delete, Chat, Tavern, music playback, and visitor counters in the preview deployment.

## Merge recommendation

Merge after CI and Vercel preview are green and the manual gallery staging/lifecycle configuration has been applied. The branch intentionally avoids changing the overall Next.js architecture: the current framework and directory structure are appropriate for continued development.
